## 一、战略决策

### 1.1 产品定位确认

**问题**：原计划混合了三个不同的问题定义：
1. 教学管理问题（学生账号管理）
2. 运维监控问题（资源占用监控）
3. 教学质量问题（实验进度追踪）

**决策**：**运维工具定位**
- 核心价值：保障系统稳定性，防止资源耗尽
- 用户痛点：教师需要知道"哪些容器在吃资源"、"何时需要干预"
- 成功指标：系统可用性、资源利用率、告警响应时间

**影响**：
- 功能聚焦在资源监控、配额管理、批量操作
- 延后教学进度追踪相关功能
- 为后续告警系统和自动化运维打基础

### 1.2 技术架构升级

**原计划问题**：
- 前端 30 秒轮询 → 后端每次实时查询 Docker
- 50 个容器时响应时间 5-10 秒
- Docker daemon 压力过大

**决策**：**后台采集 + 数据库缓存架构**
- 后台定时任务（APScheduler）每 10 秒采集所有容器性能
- 写入 `container_metrics` 表
- API 直接返回缓存数据，响应时间 <100ms

**优势**：
- 可扩展：支持 100+ 容器
- 高性能：API 响应时间从 5-10 秒降到 <100ms
- 可观测：支持历史数据查询和趋势分析
- 可靠：单容器故障不影响整体监控

### 1.3 实施策略选择

**备选方案**：
- 方案 A：后台采集架构（生产级）
- 方案 B：实时查询（快速验证）
- 方案 C：分阶段实现（渐进式）

**决策**：**方案 A - 一次性做对**
- AI 辅助下工作量仅增加 2 小时
- 避免二次重构的成本
- 符合"Boil the Lake"原则（AI 使完整性成本接近零）

## 二、扩展功能决策

### 2.1 已接受的扩展（加入本期范围）

#### 扩展 #1：容器资源配额管理

**问题**：所有容器使用固定 2GB 内存，无法灵活调整

**方案**：
- 创建容器时允许教师指定 CPU 核心数和内存限制
- 监控页面显示"已用/限制"比例（如 512MB/2GB）
- 数据库添加 `cpu_limit`, `memory_limit` 字段

**价值**：
- 提高资源利用率（小实验用小配额）
- 防止单个容器占用过多资源
- 符合运维工具的资源管理定位

**工作量**：+1 小时

#### 扩展 #2：容器批量操作

**问题**：教师需要逐个操作容器，50 个容器需要点击 50 次

**方案**：
- 监控页面添加多选功能
- 添加批量操作按钮：批量启动、批量停止、批量删除
- 后端 API 支持批量操作（接收容器 ID 数组）

**价值**：
- 大幅提升运维效率（50 个容器从 5 分钟降到 10 秒）
- 符合运维工具的批量管理需求

**工作量**：+1 小时

## 三、架构优化决策

### 3.1 后台采集任务错误处理

**问题**：原计划使用 `try-except pass` 静默吞掉所有错误

**风险**：
- Docker daemon 重启时，采集任务持续失败但无人知晓
- 单个容器故障导致整个采集循环中断
- 前端显示过期数据，教师无法察觉监控失效

**决策**：健壮的错误处理
- 单个容器失败：记录 ERROR 日志，继续处理其他容器
- Docker 不可达：记录 ERROR 日志，跳过本轮采集
- 在 `container_metrics` 表添加 `collection_status` 字段

**工作量**：+30 分钟

### 3.2 学生删除容错策略

**问题**：Docker 容器已被手动删除时，学生删除操作会失败

**风险**：
- 教师无法删除学生记录
- 需要运维介入手动清理数据库

**决策**：容错删除
- Docker 删除失败时：记录 WARNING 日志，继续处理
- 确保数据库记录能被清理，即使 Docker 实例已不存在
- 符合"数据库是唯一真相源"的原则

**工作量**：+15 分钟

### 3.3 N+1 查询优化

**问题**：监控 API 查询容器时未预加载学生信息

**影响**：
- 50 个容器 = 1 次容器查询 + 50 次学生查询 = 51 次数据库往返
- 总耗时 ~255ms，随容器数量线性增长

**决策**：使用 joinedload 预加载
```python
containers = await db.query(SimContainer)\
    .options(joinedload(SimContainer.student))\
    .all()
```

**效果**：
- 50 个容器 = 1 次 JOIN 查询
- 总耗时 ~10ms（减少 96%）

**工作量**：+5 分钟（1 行代码）

### 3.4 前端轮询可见性控制

**问题**：页面切换到后台时仍在轮询，浪费资源

**影响**：
- 10 个教师每天产生 28,800 次请求
- 其中 70% 是无效请求（页面不可见时）

**决策**：使用页面可见性 API 控制轮询
```typescript
document.addEventListener('visibilitychange', () => {
  isPageVisible.value = !document.hidden
})
```

**效果**：
- 减少 70% 无效请求
- 降低服务器负载

**工作量**：+10 分钟（10 行代码）

### 3.5 资源配额输入验证

**问题**：新增的资源配额功能缺少输入验证

**风险**：
- 教师输入 CPU=0 或内存=10TB
- 导致容器创建失败或资源耗尽

**决策**：添加合理范围校验
- CPU：0.1 - 4.0 核心
- 内存：256MB - 8192MB

**工作量**：+15 分钟

### 3.6 批量删除二次确认

**问题**：批量删除是高风险操作，误操作无法恢复

**风险场景**：
- 教师误选 50 个容器
- 点击"批量删除"
- 50 个学生的实验环境瞬间消失

**决策**：添加二次确认弹窗
- 显示："确定删除 50 个容器？这将影响 45 个学生的实验环境"
- 用户必须确认才能执行

**工作量**：+5 分钟

### 3.7 其他优化项

以下优化已确认但细节较少，在实施时补充：

7. **API 鉴权验证**：确保所有教师端 API 验证用户角色
8. **事务边界管理**：学生删除操作使用数据库事务
9. **日志记录规范**：统一日志格式和级别
10. **错误响应标准化**：使用统一的错误响应格式
11. **数据库索引优化**：为 `container_metrics` 表添加复合索引

## 四、数据库设计变更

### 4.1 新增表：container_metrics

```sql
CREATE TABLE container_metrics (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    container_id INTEGER NOT NULL,
    cpu_percent FLOAT NOT NULL,
    memory_mb INTEGER NOT NULL,
    timestamp DATETIME DEFAULT CURRENT_TIMESTAMP,
    collection_status VARCHAR(20) DEFAULT 'success',
    error_message VARCHAR(500),
    
    FOREIGN KEY (container_id) REFERENCES sim_containers(id) ON DELETE CASCADE,
    INDEX idx_container_time (container_id, timestamp),
    INDEX idx_timestamp (timestamp)
);
```

**字段说明**：
- `collection_status`: 'success' / 'failed' / 'docker_unavailable'
- `error_message`: 采集失败时的错误信息
- 保留 7 天历史数据（定期清理）

### 4.2 扩展表：sim_containers

```sql
ALTER TABLE sim_containers ADD COLUMN purpose VARCHAR(200);
ALTER TABLE sim_containers ADD COLUMN cpu_limit FLOAT DEFAULT 1.0;
ALTER TABLE sim_containers ADD COLUMN memory_limit INTEGER DEFAULT 2048;
```

**字段说明**：
- `purpose`: 容器用途说明（如"实验一：ROS基础"）
- `cpu_limit`: CPU 核心数限制（0.1 - 4.0）
- `memory_limit`: 内存限制（MB，256 - 8192）
