# 评测系统轻量级过程记录与评分方案

> 文档状态：Draft
> 适用阶段：预研 / 预上线阶段
> 目标：以最小成本打通实训考试的过程记录、教师复核、客观评分、人工评分、最终成绩入库全链路

## 1. 背景与问题

当前平台已经具备实验、版本、容器、仿真启动等主链路能力，例如后端已有实验模型 [`Experiment`](../edubot-twin-server/app/models/experiment.py:29)、版本模型 [`ExperimentVersion`](../edubot-twin-server/app/models/experiment.py:55)、仿真容器模型 [`SimContainer`](../edubot-twin-server/app/models/container.py:21) 以及学生启动仿真的入口 [`start_simulation`](../edubot-twin-server/app/api/v1/endpoints/student/simulation.py:112)。

但在“实训考试 → 过程记录 → 评分 → 教师复核 → 成绩入库”这条链路上，当前仍存在明显缺口：

- 缺少统一的考试尝试记录
- 缺少结构化过程证据
- 教师主要依赖现场观察与零散日志判断表现
- 复核成本高，容易产生争议
- 客观评分与人工评分尚未打通到最终成绩

因此，本方案的核心目标不是构建一个“大而全的录制系统”，而是建立一个**轻量、可解释、可复核、可扩展**的评分证据系统。

---

## 2. 方案结论

本方案采用：**轻量级核心状态打点方案**。

其定位是：

- **实现层**：先落地轻量级核心状态打点
- **架构层**：按分层取证思路设计，为后续争议场景预留扩展能力

一句话概括：

> 第一阶段采用轻量级核心状态打点方案，采集轨迹、碰撞、控制、系统事件四类核心证据，并以二维轨迹复核替代全量录像回放。整体架构按分层取证设计，后续可在争议场景下扩展短窗口原始片段能力。

---

## 3. 为什么不采用全量 rosbag / Gazebo 录制

### 3.1 不适合当前阶段
项目当前仍处于预研 / 预上线阶段，优先级是尽快稳定落地，而不是一次性做完整取证平台。

### 3.2 成本高，收益不成正比
全量录制会带来：

- 存储快速膨胀
- 数据检索困难
- 教师使用门槛高
- 回放系统复杂度显著上升

### 3.3 教师真正关心的是“证据”，不是“全量原始数据”
教师复核时最关心的是：

- 小车怎么走的
- 什么时候下了控制指令
- 是否碰撞，在哪里碰撞
- 是否在规定时间内到达目标点
- 如果失败，是如何失败的

这些需求用结构化核心状态就能满足大部分场景。

---

## 4. 方案定位：轻量版方案 C

从架构抽象上看，原先的“方案 C”强调三层：

1. 考试主记录
2. 结构化证据流
3. 争议场景原始片段兜底

本次最终选定方案覆盖前两层，暂不启用第三层，但在数据模型上保留扩展位。

因此本方案可以理解为：

- **现在实现**：轻量级核心状态打点
- **未来扩展**：必要时补争议时段短窗口原始片段

这意味着：

- 当前版本最适合上线
- 后续不会因为架构封死而返工

## 5. 核心设计原则

### 5.1 评分优先，不做技术自嗨
所有记录内容都必须直接服务于以下至少一种目标：

- 客观评分
- 教师人工复核
- 成绩审计
- 争议解释

### 5.2 统一时间轴
轨迹、碰撞、控制、系统事件必须统一写入同一时间轴，避免回放错位。

建议所有证据统一采用：

- `event_time_ms` 或 `event_time_ns`
- 保留可选 `source_time`

### 5.3 结构化优先，不做大 JSON 泥团
不建议把整场考试轨迹、事件、评分全部塞进一个大 JSON 字段。

应采用：

- 考试主记录表
- 证据事件表
- 评分表
- 预留原始片段引用表

### 5.4 默认轻量，按需扩展
默认只记录核心证据；只有在后续真实争议较多时，才引入短窗口原始片段。

## 6. 记录范围

### 6.1 必须记录的四类核心证据

#### 6.1.1 轨迹与位姿采样
订阅 `/odom` 或 `/amcl_pose`，记录：

- 时间戳
- `x`
- `y`
- `theta`
- 可选：线速度、角速度

建议采样策略：

- 默认 2Hz
- 接近目标区时提升到 5Hz
- 碰撞前后短时提升到 5Hz 或 10Hz

目的：

- 复原路径
- 判断是否到达目标区域
- 评估运动过程是否合理

#### 6.1.2 碰撞事件
优先监听：

- Gazebo 碰撞事件
- bumper sensor 话题

不建议第一版用 costmap 重叠率直接作为正式碰撞判分依据。costmap 更适合作为辅助风险指标。

碰撞事件记录字段建议包括：

- 时间戳
- 碰撞位置 `x y`
- 碰撞对象 A/B
- 严重程度或接触持续时长
- 可选备注

目的：

- 作为碰撞扣分依据
- 在轨迹图中打红点提示
- 支撑教师快速复核

#### 6.1.3 控制指令记录
记录两类信息：

1. 模式事件
   - 开始考试
   - 启动导航
   - 停止
   - 重置
2. `/cmd_vel` 降采样记录
   - 时间戳
   - 线速度
   - 角速度
   - 指令来源

建议不要只记录点击瞬间，而应保留 2Hz 到 5Hz 的降采样控制趋势。

目的：

- 判断学生是否在持续操作
- 解释碰撞发生时的行为
- 辅助人工评分

#### 6.1.4 系统事件
纳入现有系统链路上的关键状态，例如：

- 考试开始
- 考试结束
- 超时结束
- 容器创建完成
- gzweb ready
- rosbridge ready
- 容器异常退出
- ROS 节点异常

这些事件可以复用现有任务链路语义，例如 [`SimulationTask`](../edubot-twin-server/app/models/simulation_task.py:34) 和 [`SimulationTaskStage`](../edubot-twin-server/app/models/simulation_task.py:18)。

目的：

- 区分“学生操作问题”和“系统环境问题”
- 防止把系统异常误判为学生失误

## 7. 教师复核方式

本方案**不做视频式回放**，也不要求第一版做完整 3D 历史重演。

教师复核页面采用高信息密度的二维证据视图：

### 7.1 页面组成

1. 考试摘要
   - 学生
   - 实验 / 版本
   - 开始时间
   - 结束时间
   - 用时
   - 客观分
   - 人工分
   - 最终分

2. 二维轨迹图
   - 绘制历史轨迹线
   - 标记起点 / 终点
   - 标记目标区

3. 碰撞标记
   - 以红点标出碰撞位置
   - 点击红点可展示碰撞详情

4. 事件时间轴
   - 展示启动导航、碰撞、到点、超时、异常等关键事件

### 7.2 回放原则
回放目标不是“沉浸感”，而是“复核效率”。

因此第一版应优先做：

- 2D 轨迹图
- 事件时间轴
- 结构化详情面板

而不是直接强绑定 [`ROS3DViewer`](../edubot-twin-web/src/views/Simulation/panels/ROS3DViewer/core/SceneExtension.ts:1) 去做完整历史重演。

后续如果复核需求升级，再考虑接入 3D 历史复盘能力。

## 8. 评分模型

### 8.1 客观评分
客观评分由规则引擎根据结构化证据自动计算。

第一版建议只覆盖基础规则：

- 是否在规定时间内到达目标点
- 碰撞次数
- 碰撞严重程度
- 是否超时
- 是否长时间停滞
- 是否存在明显越界或异常行为

示例：

- 基础分：100
- 超时未到点：记为失败或大额扣分
- 每次碰撞扣固定分值
- 严重碰撞额外扣分

### 8.2 人工评分
教师基于复核界面补充人工分，例如：

- 操作规范性
- 路径合理性
- 恢复能力
- 稳定性
- 其它教学性评价

### 8.3 最终成绩
建议公式固定并版本化：

- 最终成绩 = 客观分 × 权重 + 人工分 × 权重

例如：

- 客观分 70%
- 人工分 30%

评分规则必须记录“规则版本”，防止未来规则调整影响历史成绩可追溯性。

## 9. 数据模型建议

### 9.1 `exam_attempts`
考试尝试主表，记录一次完整考试。

建议字段：

- `id`
- `student_id`
- `experiment_id`
- `version_id`
- `container_id`
- `status`
- `started_at`
- `ended_at`
- `duration_ms`
- `objective_score`
- `manual_score`
- `final_score`
- `score_rule_version`
- `review_status`
- `teacher_comment`
- `created_at`
- `updated_at`

### 9.2 `exam_evidence_events`
结构化证据事件表。

建议字段：

- `id`
- `attempt_id`
- `event_type`
- `event_time_ms`
- `sequence_no`
- `source`
- `payload_json`
- `created_at`

建议的 `event_type`：

- `exam_started`
- `pose_sampled`
- `cmd_vel_sampled`
- `collision_detected`
- `goal_reached`
- `timeout_reached`
- `system_warning`
- `system_error`
- `exam_finished`

### 9.3 `exam_scores`
评分结果快照表。

建议字段：

- `id`
- `attempt_id`
- `objective_score`
- `manual_score`
- `final_score`
- `objective_breakdown_json`
- `manual_breakdown_json`
- `score_rule_version`
- `scored_by`
- `scored_at`

### 9.4 `exam_artifact_refs`
原始片段引用表，第一版可创建但暂不启用。

建议字段：

- `id`
- `attempt_id`
- `event_id`
- `artifact_type`
- `storage_path`
- `time_start_ms`
- `time_end_ms`
- `reason`
- `created_at`

该表用于后续升级为“争议时段短窗口原始片段能力”。

## 12. 风险与约束

### 12.1 时间戳不统一
若不同事件来源使用不同时间基准，将导致回放错位。

**应对**：统一时间轴字段，后端统一归一化。

### 12.2 碰撞定义不一致
若一会用 bumper，一会用 costmap，评分会失真。

**应对**：第一版明确唯一正式碰撞判定来源。

### 12.3 过度依赖大 JSON 存储
短期省事，长期难以查询和扩展。

**应对**：采用考试主表 + 事件表 + 评分表结构。

### 12.4 教师界面做得过重
若第一版就做复杂播放器，实施周期会失控。

**应对**：先做 2D 证据页。

---

## 13. 最终建议

### 13.1 当前阶段的推荐选择
**立即采用轻量级核心状态打点方案作为第一阶段正式方案。**

原因：

- 最适合预上线阶段
- 能最快支撑客观评分与教师复核
- 能明显降低争议与复核成本
- 不会把系统拖入高成本录制 / 回放工程

### 13.2 架构要求
虽然实现上采用轻量方案，但数据模型和 API 边界必须按“可扩展到方案 C”来设计。

即：

- 实现选轻量版
- 架构选完整版

这能保证后续如确有争议场景，再平滑扩展短窗口原始片段能力，而不需要重做整套系统。

---

## 14. 实施顺序建议

1. 新增考试尝试与评分相关数据模型
2. 接入四类核心证据采集：轨迹、碰撞、控制、系统事件
3. 实现客观评分 v1
4. 新增教师端考试记录详情页
5. 打通人工评分与最终成绩入库
6. 预留原始片段索引能力但第一版不启用
